(c) 数据管线改动与迭代
================================================================================

基于 (a)(b) 的观察，我对管线做了几轮迭代实验，最终结论是：只保留原有过滤，
不额外增加导航过滤。以下是实验记录。

【迭代 1：新增导航/模板噪声过滤 —— 尝试后放弃】
--------------------------------------------------------------------------------
动机：第一轮 (a) 抽样时，5 篇保留文档开头几乎都是站点导航菜单 + 标题，看起来
导航模板噪声占比很高，担心会引入大量重复模板词、拉高 C4 基准困惑度。

第一版实现（按行匹配）：只统计"整行等于导航词"的行，效果差——真实导航行常是
组合词/带符号，且营销文案会被误当正文，结果只拦到 97 篇，基本没起作用。

第二版实现（词密度）：改用 re 把整篇文本拆成小写单词 token，统计命中导航词
（menu/search/login/shop/cart/account/register 等约 30 个"导航专属词"，特意
排除了 about/home/more/help 等正文常见词）的密度，超过 0.06 且总词数 >= 100
则丢弃。单测验证：电商页、相机配件导航页正确判出；新闻/百科正文不误杀。

重跑结果（DEBUG_N_FILES=50，data/filtered_v3）：
  dropped_low_quality: 14644
  dropped_not_english: 300847
  dropped_nsfw:        202
  dropped_toxic:       142
  dropped_nav_noise:   2873
  kept:                108672
  total_records:       427380

放弃原因：进一步抽查发现，被 nav_noise 拦掉的很多文档其实是"开头有导航菜单 +
 后面一大段正常长正文"的页面（比如 Ecomax 商品页 124 行、Aspectra 相机页 311 行），
 只有开头几十行是导航，正文占了大半。真实网页"开头带导航"是非常普遍的正常现象，
 C4 基准本身的网页也大多如此。用词密度删整篇会误杀这些正常长文，反而让训练分布
 偏离 C4 基准、拉高困惑度。因此最终决定：不加导航过滤，回退到原有过滤结果。

【迭代 2：英文误删】（针对 (b) 部分示例 5，待评估）
--------------------------------------------------------------------------------
问题：一篇明显英文的网页（印度摄影站）被 not_english 误杀，怀疑是大量非英文
专名（印度地名）压低了 fastText 置信度。
方案：可把 LANG_THRESHOLD 从 0.7 下调，或对"识别为英文但分数较低"的文档改用
更长文本做语言判断。此项需更多验证样本后再决定是否落地，避免过度放宽引入真噪声。

【迭代 3：修复 tokenize 丢失换行符的 bug —— 关键修复】
--------------------------------------------------------------------------------
问题：第一版 tokenize 脚本用 splitlines() 逐行读取再逐行 encode，而 splitlines()
会把换行符丢掉，导致产出的 token 流里**完全没有换行 token**（GPT-2 中 "\n" = 198）。
实测第一版 data.bin 前 200 万 token 中 token 198 出现 0 次。同时逐行 encode 还把
跨行的词粘连在一起（例如 "2024" 和 "December" 变成 "2024December"）。

影响：真实网页文本（以及 C4 100domains 验证集）含约 9% 的换行 token，训练数据
里完全没有 → 严重的分布错配，模型在验证集上几乎等于瞎猜。

修复：改为按「文档」而非「行」处理：用 <|endoftext|> 切出每篇文档，对文档**整体**
调用 encode（保留内部换行），末尾手动追加 eos_token_id。修复后换行 token 占比
恢复到 8.86%，与真实文本分布一致。

【迭代 4：扩大数据规模，消除过拟合 —— 关键修复】
--------------------------------------------------------------------------------
问题：最初只处理了 20 个 WET 文件，产出 169M token。而训练消耗
16384 步 × 524288 token/步 = 8.59B token，相当于在同一份数据上跑 **50.7 个 epoch**，
导致模型把训练集背了下来（训练 loss 0.34，perplexity 1.40），而 C4 验证 loss
高达 10.73—— 几乎等于随机猜测的ln(50257)=10.82。

修复：写了不依赖 modal 的 scripts/download_wet.py，直接从 Common Crawl 下载
1000 个 WET 文件（与 wet_files.py 一致的 crawl CC-MAIN-2026-17、seed 336），
重新过滤 + tokenize，得到 9.31B token，epoch 数降到 0.92（不到一遍）。

同时把 tokenize 改为流式处理：原实现先把全部文档读进 list、再把全部 token id
收集成一个 Python list，仅 token 部分就需要 8.5e9 × ~36 字节 ≈ 300GB 内存，
在 36GB 文本规模下直接 OOM 卡死。改为逐文件处理 + 边tokenize 边以 uint16 追加
写盘后，内存占用与总数据量无关。

# Problem (tokenize_data): Tokenize data (2 points)

脚本: scripts/tokenize_data.py

实现要点:
  - 按 <|endoftext|> 切出每篇文档，对文档**整体** encode（保留内部换行符），
    末尾追加 eos_token_id。不能逐行 encode，否则会丢失全部换行 token（见 (c) 迭代 3）。
  - 流式处理：逐个输入文件 tokenize 并以 np.uint16 追加写盘，内存占用与总数据量无关。
  - multiprocessing.Pool + imap（imap 保证顺序，token 流顺序必须与文本一致）。
  - 输出 ids_array.tofile(output_path)，格式为扁平 np.uint16，与训练脚本兼容。

## 做了什么（迭代过程）

第一次训练结果是失败的，暴露了两个 bug，修复后才得到上面的结果：

| 指标 | 第一次训练 | 修复后 |
| --- | --- | --- |
| WET 文件数 | 20 | 1000 |
| 训练 token | 169M | 9.31B |
| epoch 数 | 50.7 | 0.92 |
| 换行 token 占比 | **0%（bug）** | 8.86% |
| 训练 loss | 0.3388 | 2.1241 |
| **C4 valid loss** | **10.7340** | **3.3863** |
| train/valid gap | 10.40 | 1.26 |

第一次训练的 C4 valid loss 10.73 几乎等于随机猜测（ln 50257 = 10.82），原因是：
  1. tokenize 丢失了全部换行 token，训练/验证分布严重错配（见 (c) 迭代 3）；
  2. 数据量只有需求的 1/50，跑了 50.7 个 epoch，模型完全记忆训练集
     （训练 perplexity 1.40），在新数据上高置信度答错，交叉熵被放大。

此外还解决了几个工程问题：
  - **本地训练**：官方 scripts/train.py 顶层 import modal（且 SUNET_ID 为 TODO），
    本地 torchrun 无法 import。写了 scripts/train_local.py，在 import 前注入
    modal 兼容 dummy，复用官方 train_from_config，不修改任何官方训练逻辑。
  - **验证 loss 未被记录**：train.py 用 logger.info 输出验证 loss，但没有调用
    logging.basicConfig()，而 Python logging 默认级别是 WARNING，导致第一次训练
